# 13 — النسخ الاحتياطي واختبار الاسترجاع (OPS-02)

> النسخة الاحتياطية التي لم تُسترجع قط ليست نسخة. لذلك كل نسخة هنا تُكتب معها قائمة بما فيها، واختبار استرجاع دوري يعيدها إلى قاعدة مؤقتة ويقارنها بتلك القائمة صفًا بصف.

## 1. ما الذي يُنسخ

| المكوّن | يُنسخ؟ | ملاحظة |
|---|---|---|
| PostgreSQL كاملة: مخطط `public` (Prisma: المستخدمون، التنبيهات، السجل، الرسوم، الإشعارات، المناطق ونتائجها، التدقيق) ومخطط `market` (الشموع وسجل التعبئة) وكتالوج TimescaleDB | نعم | `pg_dump --format=custom` واحد لكل القاعدة |
| Redis | لا | الكود لا يستخدمه حاليًا؛ كل الحالة في PostgreSQL. إن صار يحمل حالة دائمة يُضاف هنا |
| أسرار البيئة (`.env`، مفاتيح VAPID، مفتاح age الخاص) | لا | مفتاح age الخاص يُحفظ خارج الخادم (`deploy/offsite.sh --show-key`)؛ البقية يُعاد توليدها على خادم جديد (§8) |
| `services/ml/registry/` | لا | مخرجات بحثية قابلة لإعادة التوليد من `/admin/research/dataset` |

## 2. الأهداف

| المقياس | القيمة | المصدر |
|---|---|---|
| RPO (أقصى بيانات قد تُفقد) | 24 ساعة | نسخة يومية عند `BACKUP_AT` (افتراضيًا 02:30 UTC) |
| RTO (زمن الاسترجاع) | يُقاس في كل اختبار | `restoreMs` في تقرير الاختبار ولوحة الإدارة |
| إثبات صلاحية النسخ | أسبوعيًا على الأقل | `BACKUP_DRILL=weekly` |

لخفض RPO إلى دقائق: أرشفة WAL مع استرجاع لنقطة زمنية (pgBackRest أو WAL-G)، أو ميزة PITR لدى مزود قاعدة مُدارة إن اعتُمد. هذا يُضاف فوق النسخ اليومية ولا يحل محلها.

## 3. كيف يعمل

```
                 ┌─────────── لقطة واحدة (pg_export_snapshot) ───────────┐
PostgreSQL ──►   عدّ صفوف كل جدول + بصمة المحتوى للجداول الصغيرة   +   pg_dump --snapshot
                                                                         │
                                                       age (مفاتيح عامة) │
                                                                         ▼
                    BACKUP_DIR/tw-<db>-<UTC>.dump.age  +  .manifest.json  ──rclone──►  التخزين الخارجي
```

- **لقطة واحدة**: القائمة (manifest) والنسخة تصفان البيانات نفسها بالضبط، حتى والقاعدة تكتب أثناء النسخ.
- **القائمة** (`.manifest.json`): sha256 للملف، إصدار الخادم و`pg_dump`، الإضافات (TimescaleDB وإصدارها)، ترحيلات Prisma المطبقة، عدد صفوف كل جدول، وبصمة محتوى (md5 مستقلة عن الترتيب) لكل جدول حتى `BACKUP_HASH_MAX_ROWS` صف.
- **بلا كلمات مرور في الأوامر**: الاتصال يُمرر لأدوات PostgreSQL عبر متغيرات `PG*`، فلا يظهر في قائمة العمليات.
- **TimescaleDB**: الاسترجاع يستدعي `timescaledb_pre_restore()` قبل `pg_restore` و`timescaledb_post_restore()` بعده، كما توصي Timescale. الهدف يحتاج **نفس إصدار الإضافة** المسجل في القائمة.
- **الإصدارات**: `pg_dump` يجب أن يساوي الإصدار الرئيسي للخادم المصدر أو يكون أحدث، والنسخة لا تُسترجع إلا في خادم بالإصدار الرئيسي نفسه أو أحدث (`pg_dump` 17+ يكتب `SET transaction_timeout` الذي لا يعرفه 16). الاسترجاع يرفض مبكرًا وبرسالة واضحة نسخةً من `pg_dump` أحدث من الخادم الهدف. صورة الـAPI تحمل `postgresql16-client` لأن docker-compose يشغّل PostgreSQL 16، وعند ترقية الخادم تُرقّى الحزمة معه.

## 4. التشغيل

### docker-compose

الخدمة `backup` (ضمن ملف التعريف `app`) تشغّل `backup.js schedule` من صورة الـAPI نفسها:
- نسخة يومية عند `BACKUP_AT`. عند الإقلاع، إن لم توجد نسخة أحدث من `BACKUP_MAX_AGE_HOURS` تُؤخذ نسخة فورًا، فالنشر الجديد أو الحاوية التي توقفت لا تنتظر يومًا.
- اختبار استرجاع بعد النسخة حسب `BACKUP_DRILL`.
- حذف النسخ المحلية خارج سياسة الاحتفاظ.
- فحص صحة الحاوية `backup.js status --check` كل ساعة: تصبح unhealthy إن تقادمت النسخة أو فشل الاختبار أو تأخر.
- الـAPI يقرأ `status.json` من المجلد المشترك (قراءة فقط) ليعرضه في لوحة الإدارة.

### الأوامر

```bash
node apps/api/dist/tools/backup.js run                    # نسخة الآن (+ النسخة الخارجية + الاحتفاظ المحلي)
node apps/api/dist/tools/backup.js drill [MANIFEST]        # اختبار استرجاع للأحدث أو لنسخة محددة؛ من النسخة الخارجية افتراضيًا
node apps/api/dist/tools/backup.js drill --local --keep    # من النسخة المحلية، مع إبقاء القاعدة المؤقتة للفحص اليدوي
node apps/api/dist/tools/backup.js status [--check]        # آخر نسخة وآخر اختبار؛ --check يخرج بـ1 عند مشكلة
node apps/api/dist/tools/backup.js prune                   # تطبيق سياسة الاحتفاظ محليًا
node apps/api/dist/tools/backup.js restore MANIFEST --target postgresql://…/new_db   # استرجاع الكارثة (§7)
```
(أو `pnpm --filter @tradingworld/api backup <command>`.)

### المتغيرات

| المتغير | الافتراضي | المعنى |
|---|---|---|
| `BACKUP_DIR` | `./backups` | النسخ المحلية والقوائم و`status.json` |
| `BACKUP_AT` | `02:30` | وقت النسخة اليومية (UTC) |
| `BACKUP_DRILL` | `weekly` | `daily` · `weekly` · `off` |
| `BACKUP_DRILL_URL` | خادم `DATABASE_URL` (قاعدة `postgres`) | اتصال بصلاحية `CREATE DATABASE` للقاعدة المؤقتة. يُفضَّل خادم منفصل حتى لا يحمّل الاختبار خادم الإنتاج |
| `BACKUP_AGE_RECIPIENTS` | — | مفاتيح age العامة مفصولة بفواصل. بدونها النسخ **غير مشفرة** واللوحة تقول ذلك |
| `BACKUP_AGE_IDENTITY_FILE` | — | المفتاح الخاص، مطلوب فقط حيث يجري الاختبار أو الاسترجاع |
| `BACKUP_RCLONE_REMOTE` | — | وجهة النسخة الخارجية، مثل `r2:tradingworld-backups/db` |
| `BACKUP_KEEP_DAILY/WEEKLY/MONTHLY` | 7 / 4 / 6 | الاحتفاظ المحلي (الجد-الأب-الابن) |
| `BACKUP_MAX_AGE_HOURS` | 26 | بعده تُعد النسخة متقادمة |
| `BACKUP_DRILL_MAX_AGE_DAYS` | 8 | بعده يُعد الاختبار متأخرًا |
| `BACKUP_HASH_MAX_ROWS` | 200000 | الجداول حتى هذا الحجم تُقارن بالمحتوى، والأكبر بعدد الصفوف |

## 5. التشفير (age)

```bash
age-keygen -o tw-backup-identity.txt        # يطبع: Public key: age1…
```
- **المفتاح العام** يوضع في `BACKUP_AGE_RECIPIENTS`. يُنصح بمفتاحين: مفتاح تشغيلي، ومفتاح طوارئ يُحفظ دون اتصال (ورقة أو خزنة) لدى صاحب المشروع.
- **المفتاح الخاص** في مدير الأسرار. يُركّب في حاوية `backup` (`./secrets/age-identity.txt`) فقط لأن الاختبار الأسبوعي يفك التشفير.
- النتيجة: تسريب الحاوية أو الدلو الخارجي لا يكشف البيانات دون المفتاح الخاص.
- للعزل الأقوى: لا يُركّب المفتاح على خادم النسخ، ويجري الاختبار من جهاز آخر بـ`BACKUP_DRILL=off` هنا و`backup.js drill` هناك.
- **فقدان المفتاح الخاص = فقدان كل النسخ المشفرة به.** لهذا مفتاح الطوارئ الثاني.

## 6. النسخة الخارجية (Cloudflare R2) والاحتفاظ

النسخة التي تبقى على الخادم تضيع معه. لذلك تُنسخ كل نسخة إلى Cloudflare R2 فور أخذها، ويثبت اختبار الاسترجاع الأسبوعي أن النسخة الخارجية تُسترجع فعلًا (يجلبها من R2 لا من القرص). الحجم صغير جدًا: الخطة المجانية لـR2 (10 GB) تكفي سنوات.

### على Cloudflare (مرة واحدة، من المتصفح)

1. **R2 Object Storage** ثم **Create bucket**: الاسم `tradingworld-backups`، والموقع Automatic. (أول مرة يطلب Cloudflare وسيلة دفع لتفعيل R2 حتى في الخطة المجانية.)
2. في الدلو: **Settings** ثم **Object lifecycle rules** ثم Add rule: البادئة `db/`، وحذف الكائنات بعد **200 يوم**. هذا هو الاحتفاظ هناك: الأداة لا تحذف شيئًا من R2.
3. في الدلو نفسه: **Settings** ثم **Bucket lock rules** ثم Add rule: البادئة `db/`، والاحتفاظ **30 يومًا**. خلالها لا يستطيع أحد حذف النسخة أو تغييرها، ولا حتى خادم مخترق يحمل مفتاح الوصول. (القفل يتقدم على قاعدة الحذف.)
4. **R2 Object Storage** ثم **Manage API tokens** ثم **Create API token**: الصلاحية **Object Read & Write**، و**Apply to specific buckets only** مع `tradingworld-backups`، ثم Create. تظهر مرة واحدة: **Access Key ID** و**Secret Access Key** ورابط S3 فيه **Account ID**: `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`.

### على الخادم

```bash
cd /opt/tradingworld && deploy/offsite.sh
```
يسأل عن Account ID (أو رابط S3 كاملًا) واسم الدلو والمفتاحين، ولا يظهر السر أثناء الكتابة أو اللصق. ثم:
1. يحفظها في `deploy/.env` (لا تمر عبر GitHub) ويتحقق من الوصول إلى الدلو؛ إن رفض R2 يعيد الملف كما كان ويشرح السبب.
2. إن وجد في الدلو نسخًا سابقة يسأل: هل هذا خادم جديد بدل خادم ضائع؟ عندها الصحيح `deploy/restore.sh` (§8).
3. يعيد تشغيل الـAPI ومهمة النسخ بالإعدادات الجديدة (ثوانٍ).
4. يأخذ نسخة الآن، ويرفعها، ويتحقق من حجمها على R2.
5. يجري اختبار استرجاع **من R2**.
6. **يعرض مفتاح فك تشفير النسخ.** احفظه خارج الخادم: مدير كلمات سر، أو ورقة. بدونه لا تُسترجع أي نسخة، لا هنا ولا على R2. لعرضه لاحقًا: `deploy/offsite.sh --show-key`.

النتيجة: في لوحة الإدارة تظهر **OFFSITE** بجانب آخر نسخة و**REMOTE COPY** بجانب آخر اختبار، وتزول قاعدة «النسخ الاحتياطي على هذا الخادم فقط» (`backup_offsite`، تحذير في الإنتاج).

### التفاصيل

rclone يُهيأ بمتغيرات البيئة دون ملف إعداد. هذا ما يكتبه `offsite.sh` في `deploy/.env`:
```env
BACKUP_RCLONE_REMOTE=r2:tradingworld-backups/db
RCLONE_CONFIG_R2_TYPE=s3
RCLONE_CONFIG_R2_PROVIDER=Cloudflare
RCLONE_CONFIG_R2_ENDPOINT=https://<account>.r2.cloudflarestorage.com
RCLONE_CONFIG_R2_ACCESS_KEY_ID=…
RCLONE_CONFIG_R2_SECRET_ACCESS_KEY=…
RCLONE_CONFIG_R2_NO_CHECK_BUCKET=true
```
Backblaze B2 أو AWS S3 بالطريقة نفسها (`TYPE=b2` أو `PROVIDER=AWS`).

- بعد الرفع تُقارن الأداة حجم الملف البعيد بالمحلي، ويفشل التشغيل عند الاختلاف.
- **الأداة لا تحذف شيئًا من التخزين الخارجي.** الاحتفاظ هناك بقاعدة دورة الحياة، والحماية من الحذف بقفل الدلو (الخطوتان 2 و3).
- مفاتيح R2 لا تملك صلاحية «كتابة بلا حذف»، لذلك قفل الدلو هو ما يمنع خادمًا مخترقًا من مسح النسخ.

الاحتفاظ المحلي (الجد-الأب-الابن): أحدث نسخة لكل يوم من آخر 7 أيام، ولكل أسبوع من آخر 4 أسابيع، ولكل شهر من آخر 6 أشهر. أحدث نسخة لا تُحذف أبدًا.

## 7. اختبار الاسترجاع

بالترتيب، وأي فشل يوقفه ويُسجَّل:
1. جلب الملف من التخزين الخارجي (يثبت النسخة الخارجية لا المحلية فقط)
2. **checksum**: sha256 يطابق القائمة
3. إنشاء قاعدة مؤقتة `tw_drill_<UTC>` وفك التشفير والاسترجاع إليها (مع خطافات TimescaleDB)
4. **tables**: كل جدول موجود بالعدد نفسه من الصفوف، وبالمحتوى نفسه للجداول ضمن حد البصمة
5. **migrations**: ترحيلات Prisma نفسها
6. **api schema**: الفحص الذي يجريه الـAPI عند الإقلاع
7. **hypertables**: على TimescaleDB، الجداول الزمنية عادت بعد `timescaledb_post_restore()`
8. حذف القاعدة المؤقتة، حتى عند الفشل

التقرير يُكتب في `<backup>.drill.json` و`status.json`، ويظهر في لوحة الإدارة مع زمن الاسترجاع وعمر النسخة.

## 8. الاسترجاع عند الكارثة

### ضاع الخادم: خادم جديد من النسخة الخارجية

تحتاج شيئين محفوظين خارج الخادم: **مفتاح النسخ** (`AGE-SECRET-KEY-1…`) و**إعدادات R2** (Account ID واسم الدلو والمفتاحين؛ إن ضاع المفتاحان يُنشأ token جديد من Cloudflare).

```bash
# 1. خادم Ubuntu 24.04 جديد، وسجل DNS يشير إليه، ثم كما في التثبيت الأول (docs/15 §3):
git clone -b main https://github.com/mahmoudabuaisha/TradingWorld-.git /opt/tradingworld
bash /opt/tradingworld/deploy/setup.sh trading.mediatechnologies.uk
# 2. الاسترجاع:
cd /opt/tradingworld && deploy/restore.sh
```
`restore.sh` يسأل عن المفتاح المحفوظ (مخفيًا) وعن إعدادات R2، ثم يعرض آخر 10 نسخ على R2 بتاريخها وحجمها وعدد المستخدمين والصفوف، ويسترجع المختارة (الأحدث افتراضيًا):
1. يجرّب المفتاح أولًا دون أن يثبته: مفتاح خاطئ لا يغيّر شيئًا.
2. يوقف الـAPI ومهمة النسخ، ويُبقي القاعدة الحالية باسم `tradingworld_before_<UTC>`.
3. ينشئ `tradingworld` فارغة، ويجلب النسخة من R2، ويفك تشفيرها، ويسترجعها.
4. يجعل المفتاح المحفوظ مفتاح هذا الخادم، فتُشفَّر النسخ الجديدة به، وتبقى النسخة الواحدة المحفوظة صالحة لكل النسخ.
5. يشغّل المنصة على البيانات المسترجعة.

**عند أي فشل** تعود القاعدة السابقة باسمها وتعمل المنصة عليها، ولا يتغير المفتاح ولا `deploy/.env`.

**بعد الاسترجاع:**
- كلمات السر كلها من الخادم القديم، **ومنها كلمة سر المشرف** (لا التي طبعها `setup.sh` على الخادم الجديد).
- الجميع يسجّل الدخول من جديد (مفاتيح جلسات جديدة)، وتُفعَّل إشعارات المتصفح من جديد (مفاتيح Push جديدة).
- Grafana يبقى بكلمة سر الخادم الجديد التي طبعها `setup.sh`.
- `deploy/smoke-test.sh trading.mediatechnologies.uk`، ثم اختبار استرجاع: `deploy/tw exec backup node apps/api/dist/tools/backup.js drill`.
- حين تتأكد أن كل شيء سليم: `deploy/tw exec db psql -U tradingworld -d postgres -c 'DROP DATABASE "tradingworld_before_…"'`.

### الخادم سليم والبيانات تلفت (حذف خاطئ مثلًا)

`deploy/restore.sh` نفسه على الخادم نفسه: اضغط Enter عند سؤال المفتاح (مفتاح الخادم نفسه) واختر نسخة ما قبل الخطأ من القائمة. البيانات الحالية تبقى في `tradingworld_before_<UTC>` للتحقيق.

### يدويًا (لمن يريد التحكم الكامل)

1. أوقف `api` و`backup`.
2. أنشئ قاعدة فارغة: `CREATE DATABASE tradingworld_restored;`
3. `backup.js restore BACKUP_DIR/tw-…-<UTC>.manifest.json --target postgresql://tradingworld:…@db:5432/tradingworld_restored` (يجلب الملف من R2 إن لم يكن محليًا، ويرفض أي قاعدة غير فارغة).
4. تحقق بـ`backup.js drill`، ثم وجّه `DATABASE_URL` إليها وشغّل `api`.

**وثّق** كل حادثة في PROGRESS.md: الوقت، النسخة المستخدمة، البيانات المفقودة (من وقت النسخة إلى الحادثة)، وزمن الاسترجاع الفعلي.
